Robot learning is becoming **agent-editable**. Coding agents no longer only translate instructions into robot programs: they create and revise the executable artifacts around a robot policy — the policy itself, tasks and environments, rewards, evaluation scenarios, synthetic-data generators, and even the outer training loop.

Because these artifacts can be run, inspected, and repaired, code becomes an interface between language-model reasoning, robot learning, and physical feedback. This repository maps that concrete, executable branch of agentic embodied AI.

> **The organizing question:** What does the agent write or change, where does it enter the robot-learning lifecycle, and what happens when it runs?

Most systems do not yet close this entire loop. The six overlapping topics below track the parts that have been independently demonstrated.

**Taxonomy** — topics are named after their primary research object. They overlap; a work may appear in more than one.

- **🦾 [Code as Policy](#-code-as-policy)** — the generated code *is* the deployed policy · `24 core · 2 related`
- **🌍 [Environments and Tasks](#-environments-and-tasks)** — generated code or structured artifacts define the world, task, or curriculum · `26 core · 4 related`
- **🎯 [Reward Design](#-reward-design)** — agent-authored executable logic supplies the policy-training objective · `23 core · 1 related`
- **🔍 [Policy Evaluation](#-policy-evaluation)** — agent-authored tasks, scenarios, or judges measure existing and held-out robot policies · `6 core · 3 related`
- **📦 [Synthetic Data](#-synthetic-data)** — executable data-producing artifacts, justified by downstream policy learning · `22 core · 2 related`
- **🔬 [Robot Autoresearch](#-robot-autoresearch)** — the agent runs the research loop: experiments, diagnosis, iteration · `2 core · 1 related`

Two questions resolve most ambiguous cases. **Can the policy see the signal during training?** Visible → Reward Design or Synthetic Data; invisible → Policy Evaluation. **What does the agent decide?** The shape of an artifact → Environments and Tasks, Reward Design, Policy Evaluation, or Synthetic Data; which experiment to run next → Robot Autoresearch.

- ✅ **Core = C1 + C2 + C3 + C4.** `C1` an LLM or coding agent generates, edits, or debugs executable code or a simulator-consumed structured artifact · `C2` the artifact is part of a robot-learning system · `C3` it is actually run, compiled, trained, or deployed · `C4` empirical results are reported. Works missing one criterion are kept as `Related` and explained in each section's **📝 Scope notes**.
- 📊 **Evidence is recorded, not assumed.** Each work is placed on the **[E0–E4 ladder](#reading-the-evidence)** by the kind of experiment it actually reports.
- 💻 open source · 🤖 real-robot evaluation · ⚠️ built by reading papers, project pages, and source code with coding agents, then human-reviewed. Errors are possible; corrections welcome.
- 📅 Last updated: 2026-08-18

<details>
<summary>📋 <b>Scope</b> — what is deliberately excluded, and when a work is marked <code>Related</code></summary>

Common `Related` cases, with the criterion each one misses:

- synthetic-data systems whose coding-agent component is unclear (C1);
- VLM evaluators that predict success but generate no executable evaluation logic (C1);
- automated robot-learning pipelines whose experiment controller is not an LLM agent (C1);
- environment generators that create assets or videos but not executable simulation tasks (C3);
- product posts and documentation without a controlled evaluation (C4).

`Related` entries are excluded from per-topic Core counts.

Generally out of scope:

- LLM planners that output only natural-language plans or low-level actions;
- general-purpose robotics foundation models without code generation or editing;
- ordinary simulator procedural generation without an LLM/coding agent;
- works that propose code generation but never execute or evaluate the generated artifact;
- generic software-engineering agents applied to a robotics repository without a robot-learning research question.

</details>

## Reading the Evidence

These works support their claims with very different experiments, and the difference is legible from the experiments section. We record which kinds are present so claims can be compared rather than taken at face value.

| | Level | What was actually shown |
|---|---|---|
| **E0** | Validity | The generated artifact compiles, loads, or runs. |
| **E1** | Solvability | An oracle, planner, or scripted solver completes the generated task. |
| **E2** | Discrimination | An existing policy is evaluated on it, and the artifact separates capable from incapable policies. |
| **E3** | Learning | A newly trained policy measurably improves. |
| **E4** | Transfer | The artifact or resulting policy transfers to a real robot or documented distribution shift. |

> [!IMPORTANT]
> **Higher is not automatically better.** These are evidence *types*, not a quality score. A benchmark or evaluation work that stops at E2 is doing exactly what it set out to do. One work often carries several levels at once. Verified levels are shown inline on each row; a Related entry may omit E0 when its failed criterion is executable generation.

## 🦾 Code as Policy

The agent synthesizes an external, executable robot policy — a program, skill library, computation graph, repository, or a harness around learned and classical controllers. One-shot synthesis and execution-feedback-driven rewriting both belong here; requiring a repair loop would exclude the foundational work in this lineage. Systems that mainly edit training code, rewards, or data and leave behind a *learned* policy belong to [Robot Autoresearch](#-robot-autoresearch) or [Synthetic Data](#-synthetic-data).

## 🌍 Environments and Tasks

The agent builds the world the policy learns in: environment or task code, scenes and assets, initial-state distributions, reset and termination logic, domain randomization, curricula. A usable task normally bundles reward, success, and reset, so a generated reward can ship as part of the package — the work belongs here when environment or task construction is the primary research object. The literature has moved well past one-shot generation, and critique, verification, and repair machinery are in scope. Pure asset, image, video, or scene generation with no executable robot-learning interaction is kept only as `Related`.

## 🎯 Reward Design

With task and environment usually fixed, the agent synthesizes or improves an executable training objective: reward or cost source code, feature logic, components, parameters, or constraints consumed by policy learning or optimization. Fixed templates and APIs are allowed when the agent still decides the executable reward logic; merely invoking a learned VLM scorer is not. Training-time success or termination predicates belong here when they provide credit or end episodes, while held-out measurement belongs to [Policy Evaluation](#-policy-evaluation). The lineage spans one-shot translation, execution- and training-guided refinement, evolutionary search, multimodal alignment, and sim-to-real configuration.

## 🔍 Policy Evaluation

The agent authors executable evaluation artifacts—task programs, scenario distributions, success predicates, or rollout evaluators—and uses them to measure existing or held-out policies. Oracle solvability alone remains [Environments and Tasks](#-environments-and-tasks); training-time objectives remain [Reward Design](#-reward-design). Purely learned visual or world-model judges are kept as `Related` when no executable evaluation artifact is generated.

## 📦 Synthetic Data

The agent writes or configures an executable data-producing artifact: a task or expert program, simulator-consumed scene/workflow, trajectory, or reusable annotation. Core requires E3 evidence that this artifact materially changes the training supervision or distribution and benefits a newly trained policy; merely running RL inside a generated environment is insufficient. Overlap with [Environments and Tasks](#-environments-and-tasks) and [Code as Policy](#-code-as-policy) is expected when those claims are independently evaluated.

## 🔬 Robot Autoresearch

The agent runs the outer research loop: designing experiments, modifying training code, diagnosing failures, and iterating on a policy. Autoresearch — coding agents that run experiments, analyze results, and decide what to try next — became a distinct research area in 2026; this topic covers its robot-learning instantiation. Core requires result-conditioned changes across repeated experiments, not a fixed sweep or one-time training pipeline. High-level human direction is compatible with the topic when the agent makes the detailed code and experiment decisions and that intervention is disclosed. Where the generated code *is* the deployed policy, see [Code as Policy](#-code-as-policy).
